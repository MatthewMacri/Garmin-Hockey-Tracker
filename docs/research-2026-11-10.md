# Research, 2026-11-10

Eleven parallel investigations, run after a game on 2.5.5 came back with the
owner reporting the watch "buzzing and beeping a lot". Findings are kept here
because several of them contradict comments that are still in the source, and
because three of them change what this app should do next.

Claims are marked **[official]** (Garmin documentation), **[staff]** (a Garmin
employee on the forums), **[measured]** (computed here from a recorded game or
the installed SDK), or **[anecdote]**.

---

## 1. The buzzing: three sources, and 2.5.4 fixed the quietest one

| Source | Fired, 2026-11-09 game | Gated by | Status |
|---|---|---|---|
| Change buzz, ice<->bench | 0 | `changeAlerts`, default off since 2.5.4 | fixed |
| Long-shift alert | **16** | `shiftAlerts`, **defaulted on until 2.5.6** | fixed in 2.5.6 |
| `session.addLap()` -> firmware lap alert | **49** | nothing the app can reach | **cannot be fixed in the app** |

**[measured]** From `data/2026-11-09-game/`: 25 shifts, median 76 s, 16 past the
60-second default target. Each crossing fired `TONE_ALERT_HI` plus a
500/150/500 ms double buzz - the loudest alert in the app - to report that a
76-second shift was long. At four defencemen it was the median, not long.

2.5.4's own comment argued that off is the right default for an app whose
claim is that you start it and forget it. That argument was applied to the
quiet alert and not to the loud one. Corrected in 2.5.6.

### The lap alert cannot be silenced by this app

**[official]** `Session.addLap()` takes no arguments, in every API level. The
`createSession()` options are `:sport`, `:subSport`, `:name`, `:poolLength`,
`:autoLap` (entry/exit geometry only) and `:sensorLogger` - none affects
notification. `Attention` has only emitters. `System.getDeviceSettings()` is
read-only, and `vibrateOn`/`tonesOn` *report* the user's setting rather than
setting it.

**[staff]** The firmware draws its own lap view over a Connect IQ app, and
`onHide` is called when the native lap banner appears. Also, from the same
era: "an option to disable these is under consideration" - about eleven years
ago. `addLap(showLapScreen)` was proposed by a developer and never added.

**[anecdote]** A 2025 thread on an Edge 540 reports a banner covering two
thirds of the screen for ten seconds, undismissable, and that turning Auto Lap
off does not stop it. The thread is unanswered. Other developers report seeing
no banner at all on some devices, so the *visual* is not universal; the
tone/vibration is better supported, and 49 - 16 = 33 otherwise unexplained
events matches the lap count far better than anything else.

**No FR570 has been tested by anyone in those threads.** The decisive test is
three laps in the simulator and then on-device with Sound & Vibe toggled.

**What the player can do** **[official]**, FR570: hold the LIGHT button ->
`Watch Settings > Sound & Vibe` -> `Alert Tones` / `Vibration` / `Silent Mode`.
These are system-wide, so they also silence this app's own alerts; there is no
way for the app to be loud while the firmware is quiet. Per-activity `Lap
Alert` does **not** help - **[official]** it "sets the data fields to show for
laps", i.e. banner content, and **[anecdote]** per-profile activity settings do
not reach a Connect IQ session, which has no activity profile.

### A hazard worth knowing, and our 2.5.5 fix does not cover it

**[staff]** Pressing START/STOP while the lap banner is up drops the user into
the **native** save/discard dialog and exits the app. With 49 banners in a
game, that is a second plausible cause of the field report that the app
"pressed it enough times to end and discard the workout" - and hold-to-pause,
added in 2.5.5, cannot intercept it, because the press never reaches the app.

**[measured]** The related `onHide` hazard does **not** apply here. A developer
in that thread lost GPS at every lap because `onHide` tore down sensors. This
app is already safe: `IndoorHockeyApp.mc:30` drives `model.onTick()` from an
app-level timer, and `GameView.onHide()` stops only the redraw timer -
documented at `GameView.mc:99`. Detection, HR accumulation and field writes
continue under a banner. The only casualty is `viewVisible`, which gates the
idle auto-end.

### Options for the 49 laps, ranked

Hard constraint **[official]**: `FitContributor.MESG_TYPE_LAP` data "is written
once for every lap in the session" - lap fields are *flushed* by a lap event
and cannot create one. There is no API to emit a lap FIT message. **A Splits
row requires a real `addLap()` at the moment of the split.**

1. Keep 49 laps, document the Sound & Vibe setting. Full fidelity; silences the
   app's own alerts too.
2. **Lap at one edge of each transition only** - ~25 instead of 49. Splits keeps
   one row per shift; bench time becomes a column on that row via a lap
   developer field rather than its own row. Best compromise.
3. Record-level fields only, no laps. Silent, graphs still work, this repo's
   tooling still reads everything - but the Splits tab is gone, and Connect
   will not synthesise splits from a developer field.

## 2. The developer-field limit is per message type, and overflow is uncatchable

**[official]** No Garmin document states a field *count* limit anywhere. The
only documented limits are bytes, stated **per message**: 256 per message for
an app, 32 for a data field. "Messages larger than the limit will result in a
'New Field out of memory for FIT data' error."

**[staff]** The "16 fields" figure traces to one forum post: "it is set to 16
for every device that I checked" - followed, in the same thread, by "I only
evaluated the number of RECORD fields allowed. It is possible that you can have
more than 16 fields if some of them are SESSION or LAP fields." The mechanism
is a memory pool, not a counter: "a SESSION contribution should be smaller than
a LAP or RECORD contribution."

**[measured]** This app, grouped by message type - the numbers that matter:

| Message type | Fields | Payload bytes of 256 |
|---|---|---|
| SESSION | **16**, or 19 with a stride length set | 48 |
| RECORD | 8 | 12 |
| LAP | 4 | 6 |

Bytes are not the constraint; count is. The 2026-11-09 game proves less than
previously claimed: 24 fields created and 24 landed, but that build ran SESSION
at **13**.

**[staff]** Overflow does not throw. It raises an uncatchable System Error -
confirmed by a Garmin engineer proposing a throw as a *future* improvement
("it would make it possible for you to handle the error vs just crashing the
app"), and by several developers who built this exact fallback and found the
errors uncatchable. It can also crash at **write** time, and session fields are
written once, at the end of the recording - the one moment a crash costs the
whole game.

**So the tiering in `createFields()` cannot fire.** It stays as a priority
order; the real protection is a static SESSION budget. Corrected in the source
comment.

## 3. Stride detection: the 0.72% result does not mean what it looked like

Three defects, two of which are not about the wrist, would have produced
roughly the observed number from a perfect signal.

### 3a. The sample rate in the comments is wrong

**[measured]** `_hz = 21.0` is only an initialiser; `StrideMeter.mc:246` is an
EMA that converges in play. Backing the real rate out of the six accepted
detections (each gives `_hz = (spm/60) x refined`, with `refined` within +/-1 of
the integer lag because the parabolic shift is clamped) and intersecting all
six constraints gives **`_hz` in [24.08, 25.65] - about 25 Hz, not 21.4.**

Consequences: the real search band was **0.89-3.44 Hz**, not the documented
0.79-3.06; and the EMA corners were 0.42/4.63 Hz, not 0.35/3.89.

**[measured]** The `MAX_WINDOW` comment claiming "rates on supported devices top
out at 25 Hz" is contradicted by the installed SDK: `fr57042mm/simulator.json`
gives `maxAccelRate: 100`, and **92 of the 126 products in `manifest.xml`
publish a maximum and every one says 100**. `pickSampleRate()` caps the request
at 25, leaving a 4x factor unused.

### 3b. The window is longer than a hockey striding bout - ceiling 14%

**[measured]** Contiguous runs of on-ice-and-above-threshold seconds in that
game: 275 bouts, 829 s, **median 2 s**, mean 3.0, p90 6 s, max 18 s. Judged
seconds whose whole preceding window lies inside one bout:

| Window | Pure-striding windows | Share of 829 |
|---|---|---|
| 2 s | 554 | 66.8% |
| 3 s | 378 | 45.6% |
| 4 s | 255 | 30.8% |
| **6 s (128 samples)** | **117** | **14.1%** |
| 8 s | 59 | 7.1% |

**A 6-second window cannot exceed ~14% coverage in this game, with a perfect
detector on a perfect signal.** Observed was 0.7% - one twentieth of that. The
window discards 86% before any threshold is consulted.

Independently consistent with the hockey literature: two-foot glide is 39% of
on-ice time and the average skating characteristic lasts about 1.5 s; an elite
game is 82.4% low-intensity. The most frequent events are crossovers and
turns, which are **asymmetric**, so the push train is not cleanly periodic
either.

### 3c. The band clips the fundamental, and OCTAVE makes it worse

**[measured]** At 25 Hz, `MAX_LAG = 27` puts the slow edge at **0.93 Hz**.
Published full-cycle skating rates run **0.63-1.29 Hz** for submaximal and
steady skating, so much of the real distribution sits below the floor. When the
fundamental is out of band, autocorrelation returns a submultiple - and
`StrideMeter.mc:319` computes `half = bestLag / 2`, so OCTAVE only ever steps
toward *faster* lags and actively prefers the harmonic.

The sustained detection at 85-89 spm is 1.42-1.48 Hz, exactly the 2x harmonic
of a 0.71-0.74 Hz cycle - a plausible cruise-stride rate for a defenceman.
**An octave ambiguity cannot be resolved when one of the two octaves is outside
the search band.** And `bestLag < MAX_LAG` skips the parabolic interpolation, so
any true period beyond lag 27 piles onto lags 26-27 uninterpolated, which is
almost certainly the `lag 26, r=0.54` detection.

Worse, OCTAVE defends the wrong direction. Patent and arXiv sources describe
the wrist failure as *frequency halving* - "two peaks per stride, one during
the forward arm swing and one during the backward" - so **at the wrist the
likely error is undercount-by-2, not overcount-by-2.**

### 3d. Can the wrist carry skating rhythm at all? Still unmeasured

Against: no study has ever measured wrist accelerometry during skating (the
Manitoba arm-swing thesis lists it as future work); every skating IMU study
places sensors on skate, pelvis, lower back or between the scapulae; a
UWB+IMU hockey study that *had* a wrist sensor says "the data from the wrist
worn IMU is currently not used"; commercial products use skates (Scorched Ice)
or shoulder pads (HELIOS Core). Head-to-head step counting puts the wrist
worst by a wide margin - 41% error at slow speed versus 5% at the ankle - and
the specific failure is hands fixed to an object: a *held* object costs ~15%,
an object *anchored to the ground* up to 95%.

For: a hockey stick is held, not anchored, so hockey should sit between those
rather than at the bad end. And Bracko states the coupling mechanism directly:
"The shoulders have to abduct and adduct with the hips to maintain balance,
momentum, and increased velocity, whether the player has one or two hands on
the stick."

The cross-country-skiing analogue is **weaker than it looks** and should not be
leaned on: skiing does use a wrist gyroscope for cycle rate, but there the arm
is the propulsive limb driving a pole into snow. In hockey it is a balance
contributor.

**[measured]** The six accepted seconds are three independent events, and five
of six land in two adjacent lag bins with a four-second run holding 85-89 spm.
Noise across a 21-bin search scatters; this did not. Weak evidence, n~2, but it
points the right way.

### 3e. The decisive measurement has not been taken

`stride_r` and `stride_lag` were set only on acceptance, so 823 of 829 judged
seconds recorded zeros. Fixed in the working tree, and `stride_prom` added -
but **no recorded game carries it yet.**

One game on a build with the diagnostics gives the per-second lag histogram
over all ~829 judged seconds:

- a mode near 1.2-1.5 Hz -> the wrist carries the rhythm and the thresholds
  were wrong
- **a pile-up at lags 26-27 -> the fundamental is below the floor and the band
  is the bug**
- a flat histogram -> the wrist does not carry it

### 3f. If it is rebuilt, autocorrelation is the wrong family

Brajdic & Harle, 27 subjects, 130 traces, 11 algorithms: "The overall best step
counting results were obtained using the windowed peak detection (WPD), HMM and
CWT algorithms, each with a median error of ~1.3%", and "a windowed peak
detection algorithm is overall the optimal option for step counting regardless
of smartphone placement." Normalised autocorrelation was **worse** for
counting; its strength was walk *detection*.

The architectural argument is the decisive one: autocorrelation estimates a
*period* and needs several consistent cycles in one window. Hockey gives 1.5-3 s
bouts containing 1.3-3 cycles. Counting discrete events tolerates that; period
estimation cannot. A counter also divides events by elapsed wall-clock time, so
it is **immune to the `_hz` confound** that corrupts every lag->Hz conversion
above.

Recommended replacement, with sourced starting values:

```
Sample rate   request 50 Hz (device maximum is 100; current cap is 25)
Band-pass     target 0.5-3.5 Hz. At 50 Hz: A_SLOW 0.061, A_FAST 0.351
              f = fs*acos(1 - a^2/(2(1-a)))/2pi
Cluster/refractory  0.25 s, not 0.30 - the physiological floor is 0.235 s
              (4.25 pushes/s in the first three strides of a standing start),
              and 0.30 s clips acceleration bursts. Let cluster-max, not the
              refractory, suppress the double peak.
Peak rule     local max of the band-passed magnitude, AND max within its
              cluster, AND score > running mean + 1.2*SD over a trailing 3 s
Regulation    4 consecutive valid intervals before publishing, NOT 8. Median
              striding bout is 2 s; 8 pushes is 4 s, which only 29% of bouts
              reach. This is the parameter most likely to silently reproduce
              the 0.72% failure.
Output        pushes counted over a trailing 10 s window divided by elapsed
              on-ice-and-moving time. Never report a period.
```

**The cluster-max rule**, which the naive refractory gets wrong: collect every
candidate above threshold, group candidates within R of each other, and emit
one push per cluster - *the largest member*. A bare minimum-distance rule emits
on whichever candidate arrives **first**, even if a larger one follows 80 ms
later, and resets the refractory from the wrong origin so the error cascades.
At 25 Hz peak quantisation is +/-20 ms against a 100-150 ms intra-stride offset,
so which sample crosses first is noise. Cluster-max is indifferent to that.

Causal streaming form, two state variables, latency R, no buffer:

```
on candidate (idx, val):
    if not pending:            pending = (idx, val)
    elif idx - pendIdx <= R:   if val > pendVal: pending = (idx, val)
    else:                      emit(pendIdx); pending = (idx, val)
each sample: if pending and now - pendIdx > R: emit(pendIdx); clear
```

Cost **[measured]**: the current inner loop is sum(128-L) for L=7..27 =
**2,331 MACs/second** plus 128 prefix sums and 21 `Math.sqrt`, roughly 10% of
the per-call bytecode budget, with `_ring`+`_d`+`_p`+`_r` = 414 Float slots
(~3.3-5.0 kB). A counter is ~300 ops/s and ~130 bytes - about **78x cheaper**,
and it removes the largest allocation in the class.

**[measured]** Memory context: the 98,304-byte limit this app is designed
against comes from only **5** devices (`instinct2`, `instinct2s`, `instinct2x`,
`instinctcrossover`, `descentg1`) - the same old devices that publish no
high-rate accelerometer. **The FR570's own watchApp limit is 786,432 bytes, 8x
the budget.** So memory is a portability constraint, not an FR570 one.

### 3g. Garmin does not already provide this

**[official]** `Activity.Info.currentCadence` is documented only as "the
current cadence in revolutions per minute" with no statement of which sports
populate it. **[anecdote]** A bug report on inline skating has it returning
`null`, unresolved. `SensorHistory` has no cadence/step/stride getter;
`Toybox.Sensor` cadence means a paired bike sensor or foot pod.
`AntPlus.RunningDynamicsData` gives strides per minute but needs a pod or
HRM-Pro. FIT has `record.cadence` but **no `stride_rate` field**. No official
Garmin source documents a skating cadence or stride metric for any wrist
hockey profile. Deriving it from `registerSensorDataListener` is the only route.

## 4. Competitive position: the premise holds, the differentiator does not

### Garmin's native Ice Hockey profile does not detect shifts

**[official]** FR570 manual, p.7: Ice Hockey is one of twelve names in one row
of the Team Sports table. There is no hockey-specific section; "shift", "ice
time" and "player load" appear nowhere in a sport sense. **Auto Lap offers only
`Auto Distance`**, default 1600 m - so on the native profile the only way to
mark a shift is to press the lap button at every line change, which is the
thing this app exists to avoid. Garmin has no "player load" metric at all;
that is Catapult's term.

**[anecdote]** Consistent user reports that the profile yields heart rate and
calories, with distance and speed zero indoors. The profile arrived in a
firmware drop that added ~30 activity profiles at once; as one reviewer put it,
"sometimes, the new sport is simply a label."

So the reviewer who "went back to the native hockey activity tracker" went back
to a stopwatch with an HR curve and a calorie count - **but one that never
mis-detects anything and never buzzes.** A competitor's 1-star review makes
exactly that argument. **This app is not losing to Garmin's features; it is
losing to Garmin's lack of false positives.** That reframes the known
weaknesses from polish into the central competitive problem.

### Automatic shift detection is no longer a differentiator

Four Connect IQ apps now do it; three shipped in 2026.

| App | Downloads | Rating | Shift detection | Per-shift laps |
|---|---|---|---|---|
| RinkPulse | **1,000+** | 4.1 / 7 | accel + gyro + HR + speed | no (per period) |
| Ice Hockey Tracker | 100+ | 4.0 / 7 | accel + falling HR | **yes** |
| **Ice Hockey Shifts** (this app) | 100+ | 5.0 / 1 | wrist MAD + learned threshold + HR gate | **yes** |
| Blueline | 10+ | none | accel + HR, learned per game | no (per period) |

Blueline published four days before this research and matches this app on
learned thresholds, face-off discrimination and manual override, then extends
past it into recovery: HR drop at 30 s and 60 s, percentage recovered, a
recovery half-time from a fitted exponential, period-over-period fatigue, 30
games of on-watch history, a 10-game trend and a glance. Zero reviews, so there
is no evidence any of it works.

**Still defensible:** one lap per shift in Connect (only this app and Ice
Hockey Tracker), the depth of the FIT field set, and - the open goal - **a
measured accuracy claim.**

**Stop claiming:** hands-free detection, motion+HR fusion, glove-proof
correction. All four apps have them.

### Nobody in the category has published an accuracy number

Catapult is the gold standard, used by most NHL teams for goalie monitoring,
and shipped Auto Shift Detection recently. Its only supporting data is an
unpublished internal analysis of a single AHL practice; **no error rate, no
methodology, no named validator.** Every Connect IQ competitor's reviews fail
on the same two things - phantom events and slow bench recognition - and
RinkPulse's own listing concedes "real-game accuracy validation is ongoing".

**Whoever first publishes measured accuracy against hand-logged games owns the
credibility of the whole niche.** This app already records `on_ice`, `motion`
and `motion_threshold` per second, so the data to do it exists.

### What players actually ask for, ranked

Forum-sourced, low dozens of threads. **Reddit was unreachable, so r/hockey,
r/hockeyplayers and r/Garmin are not represented** - the largest gap here.

1. **Skating speed and distance** - strongest by a clear margin, and asked for
   more often than shifts. "I don't care if the given accelerator speed
   measurements are even 50% accurate."
2. Shift count and length
3. HR during shifts, excluding bench - usually phrased as a complaint
4. Recovery between shifts - only ~2 asks, but **four products built it
   independently**, which is the better signal
5. Total ice time - table stakes; its absence loses a user, its presence wins
   none
6. Season and cross-game trends - retention, not acquisition
7. Goals/assists scorekeeping - **~0 asks**, and a button burden with gloves
8. **Stride rate / cadence - ~0 asks, and twice explicitly rejected.** "For ice
   hockey, they mainly want heart-rate training data and don't need GPS or
   stride length." Wanted only instrumentally, as a route to distance.

**The actionable mismatch: #1 and #8 are the same subsystem.** This app already
produces `Distance (estimated)`, `Speed While Striding` and `Stride Length
Used` - the most-demanded outputs - and surfaces them in the vocabulary of the
least-wanted one. Lead with top speed and distance; demote stride rate to a
diagnostic. Players also say "work-to-rest" and "do I die in the third", not
"cardiac drift" and "fatigue trend".

Also frequently asked and not on the roadmap: correct activity categorisation
and clean Strava sync (~3 threads, high heat), documentation of what is
actually measured, calories, CSV/JSON export, and gear/skate-sharpening
tracking (two competitors added it independently).

**Not found - do not assume:** no public complaint anywhere about gloves
preventing button presses, no battery complaints, no "I forgot to start it"
complaints. This project's own field report is better evidence than anything
public.

### Goalie mode

**[anecdote]** What is actually instrumented: Catapult outputs Goalie Load,
Goalie Load Per Minute, **Down Count** and **Asymmetry**. A goalie can drop
more than 100 times in a game; asymmetry is flagged as an overuse-injury
driver; it is used for load management like pitch counts. More than 80% of NHL
teams monitor it.

So a goalie's question is not "how many shifts" but "how much did I go down,
how lopsided was it, and how hard was my heart working for 60 minutes".
RinkPulse's worst substantive review is its goalie mode: "It requires a shift
time for goalies but that doesn't make sense because you stay on the ice for
the entire game?"

A goalie mode is a *mode*: switch detection off, run one continuous game with
period segmentation, report full-game HR, zones, time above 85% HRmax and
per-period load. **Do not promise a wrist-based down count** - Catapult's
sensor is torso-mounted, drops are a trunk/hip event, a glove-hand wrist is a
poor proxy, and shipping an unreliable count reproduces the phantom-shot-count
problem that earns 1-star reviews here.

## 5. Chest strap support is probably already working

**[official]** FR570 manual p.12: "If both wrist-based heart rate and chest
heart rate data are available, your watch uses the chest heart rate data", and
p.46: wrist HR `Status` defaults to `Auto`, which "automatically uses the wrist
heart rate monitor unless you pair an external heart rate monitor".

**[measured]** This app reads `Activity.getActivityInfo().currentHeartRate`
(`GameModel.mc:2695`) and never calls `Sensor.setEnabledSensors`. During a
recorded activity that property returns the source the *system* selected - which
per the above is the strap whenever one is paired.

So issue #2 is likely **documentation plus a status indicator**, not a feature.
It needs confirming with one game on a paired strap - the FIT's `device_info`
messages will name the HRM - but the honest status is "probably already works",
not "untested".

The accuracy at stake is large and lands exactly on this app's headline
metrics. Wrist PPG in intermittent team sport: **bias -16.5 bpm, limits of
agreement -59.6/+26.7, MAPE 17.5%, and 35.5% of samples off by 20 bpm or more**
- against MAPE 1.2% for the same watch in steady running. Error roughly
**triples** during rapid HR change (first five minutes of a run: MAPE 7.6% vs
2.7% overall). Above 150 bpm the agreement collapses for every wrist device
tested against 12-lead ECG - and 150+ is the hockey working range. Garmin's own
manual concedes the cold problem and advises warming up indoors, which is
unfollowable in a 5-10 C rink.

There is **no validation study of wrist optical HR in ice hockey at all**; this
project is ahead of the literature, which is itself an argument for publishing
its own numbers.

## 6. Two shipped metrics need their claims narrowed

**`hr_drift` may be reporting an artifact.** A study of 17 top-tier
professionals over 122 player-games with 1 s chest-strap sampling found **no
cardiac drift and no HR-based fatigue signature across periods** - mean and
peak %HRmax flat, and time above 85% HRmax slightly *higher* in period three.
In the best-instrumented dataset available the effect is not there at period
level. The mitigation already in the code - fitting only seconds inside a fixed
band of effort - is the right one, but the readout should be scoped explicitly
to within-shift, and a non-zero value should not be presented as a trend.

**`bench_recovery` is confounded by posture at the same magnitude as the
signal.** A randomised crossover on 15 varsity players found active (standing,
pacing) versus passive (seated) recovery differed by **12 +/- 3 bpm at 45-120 s**.
There are no published norms for bench recovery at all, so the metric is
genuinely novel - but a strap improves the *measurement* without making the
*number* interpretable. Capturing or at least flagging whether the player sat
would.

Useful chest-strap reference values for threshold calibration: in-game HRmax
195 bpm in U18 internationals (about 9 bpm *above* their lab incremental max),
mean game HR 158-161, forwards 7.3-7.6 shifts per period and defence 8.2-8.5;
time above 85% HRmax 8.5-9.7 min per period for defence. And a caution for the
HR/motion cross-check: officials were found to spend 94-96% of time in
low-intensity movement yet were above 70% HRmax for 70% of ice time, so
motion/HR disagreement does not mean the HR is wrong.

## 6b. A portability constraint that governs every new API

**[measured]** `System has :getDisplayMode` is **not sufficient** to use an
API the oldest target device lacks. `has` is a runtime test; symbol resolution
is compile time. Tried and rejected:

```
ERROR: instinct2: GameView.mc:148,8: Value '$.Toybox.System.getDisplayMode'
       is not supported for device 'instinct2'.
ERROR: instinct2: GameView.mc:148,8: Value '$.Toybox.System.DISPLAY_MODE_OFF'
       is not supported for device 'instinct2'.
```

The build for `fr57042mm` succeeded; `instinct2` failed. Since `package.sh`
builds all 126 products, that is a broken release, not a degraded one - and it
would have been invisible if only the default device were built.

This matters far beyond one feature. The manifest spans **API level 1.2 to
6.0**, and `getDisplayMode` is 5.0.0. So **any** API newer than the oldest
target needs source-level separation - annotations plus per-device
`excludeAnnotations` in a jungle - not a `has` guard. That cost has to be
priced into every proposal that depends on a modern API, and it is why a
feature being "available on the FR570" is only half the question.

**Build both `fr57042mm` and `instinct2` before any release.** `instinct2` is
both the tightest memory limit (98,304 B, shared with four others) and among
the oldest API levels, so it catches the memory ceiling and the API ceiling at
once. `tools/size.sh` already uses it for the former.

The specific case that prompted this - skipping the once-a-second redraw while
an AMOLED panel is off - was reverted. The benefit is not measurable off the
watch (the firmware may already elide `onUpdate()` while the screen is dark),
and it is not worth per-device build machinery for an unmeasurable gain. Worth
revisiting only alongside another API-5.0+ feature that justifies the jungle.

## 6c. Detector accuracy: what the literature supports, and one refusal

### A 30-second minimum dwell was recommended and is wrong for this data

**[measured]** Shift lengths in the 2026-11-09 game, ascending:

```
9, 19, 23, 23, 27, 32, 45, 47, 47, 64, 67, 74, 76, 79, 81, 89,
101, 101, 103, 108, 120, 131, 134, 146, 150
```

| Minimum dwell | Shifts merged | Bench spells merged |
|---|---|---|
| 20 s (shipped) | 2 of 25 | 0 of 24 |
| 25 s | 4 of 25 | 1 of 24 |
| **30 s (proposed)** | **5 of 25** | **4 of 24** |
| 35 s | 6 of 25 | 4 of 24 |

Raising the dwell to 30 s would merge **20% of shifts and 17% of bench
spells**. Short shifts are real hockey - a quick change, a line caught out, a
penalty-kill shuffle, getting beaten and coming straight off. **Not adopted.**
25 s is the defensible ceiling and even that costs four shifts.

The general lesson is the one this project keeps relearning: a recommendation
that says "measured gain" has to name the game it was measured on. Three of
the four recorded files carry `application_version 0` - sideloaded, medians of
14-17 s - and predate `MIN_SHIFT_SEC = 20` entirely. Only 2026-11-09 was
recorded by anything resembling the shipped detector.

### The smoothing gain the literature reports is already banked

Measured HMM/Viterbi smoothing gains on wrist accelerometry:

- CAPTURE-24, 151 participants: random forest macro-F1 .711 / kappa .665 ->
  **RF+HMM .789 / .772** - more than any feature change in that paper
- Willetts 2018, 126 features: **kappa 0.69 -> 0.81**
- ActiNet: HARNet+HMM macro-F1 0.82 / kappa 0.86 vs RF+HMM 0.76 / 0.80

Those gains are against **raw, unsmoothed per-window classification.** This
app is not that. It already has hysteresis, asymmetric confirmation counters,
dead-band streak decay and a minimum dwell. An HMM tested against *that*
found nothing - 19 vs 22 shifts, no sub-20-second runs either way.

**So the +8 to +11 kappa the literature attributes to smoothing is already
collected here; it is just spelled as counters rather than as Viterbi.** That
is a point in favour of the existing design, and it removes the most
attractive-looking item on any accuracy roadmap.

### A hard limit: the wrist cannot tell standing still from sitting

This is the residual error, and no feature fixes it.

- ProPASS 2026, 53 free-living participants against video: wrist overall
  **91.8%**, sitting/walking/running/cycling 88-97%, **standing 71-77%** -
  and the stated cause is "the majority of misclassification for wrist
  captured standing was when it registered as sitting during periods of
  standing still"
- Ellis 2016: wrist standing sensitivity **.687**, ~21% of standing minutes
  labelled sitting. Sasaki 2016: wrist standing recall **22**
- Mechanism: the wrist measures **forearm** orientation, two joints from the
  trunk. Sitting or standing with the arm hanging produce identical forearm
  attitudes, and pronation/supination rotates which axis faces gravity with no
  postural change at all
- **A gyroscope does not rescue it** - adding one gave "negligible changes" at
  the wrist, RMSE change 0.0 MET
- The two largest wrist pipelines in existence declined the problem: Willetts
  uses one merged "sit/stand" class, Walmsley uses sleep/sedentary/light/MVPA

**A defenceman standing still at the point will read as bench, and that cannot
be fixed in the feature layer.** It has to be carried by duration priors
instead - which is an argument for the shipped counter/dwell design and
against chasing features.

### The feature upgrade is worth 0 to +7 points, not a win

And the current metric is the field standard, not a naive choice: GGIR's
**MAD** is the absolute difference between the Euclidean norm and the epoch
mean of the Euclidean norm - identical to what `ShiftDetector.onSensorData`
already computes. Vahe-Ypya's MAD validation reports within-person r
0.927-0.991 against VO2.

Evidence that more features is not automatically better, on this contrast:

- A 7-feature wrist random forest scored **70.6%** against video truth -
  *worse* than a wrist count cut-point at **77.5%** and wrist ENMO at 76.2%
- Across 21 algorithms for daily sedentary time, machine learning scored R2
  0.44-0.63 while the best single cut-point - **MAD at 42.4 mg** - scored 0.64
- The clean positive is +7 pp, and it took a deep self-supervised model
- A feature-based random forest beat a from-scratch deep net on 7 of 8 wrist
  benchmarks

If one feature is added, the candidate is **rectified 0.25-2.5 Hz band-pass
energy** - most nearly orthogonal to MAD, because it rejects exactly the
non-periodic bench motions (drinking, stick-banging, cheering) that MAD counts
as movement. Four independent lines converge on that band, and the existence
proof is that **ActiGraph counts** - forty years of activity epidemiology - is
itself an integer, FFT-free band-energy feature.

Two mechanical warnings for whoever implements it:

- **A 1-second window at 21 Hz cannot resolve the 0.6-2.5 Hz band.** DFT bin
  spacing at 1 s is 1 Hz, so the band is two or three bins wide. Run a
  2nd-order IIR band-pass continuously and accumulate rectified output over a
  4-8 s trailing window - cheaper than an FFT and actually resolves the band.
- **Orientation needs no `atan` or `sqrt`.** Arm-angle thresholds are
  monotonic in what they compare, so test `mean_y^2` against
  `k^2 * (mean_x^2 + mean_y^2 + mean_z^2)` with a precomputed integer `k^2` -
  identical decision boundary, no transcendental, no float. Same dodge for
  spectral entropy: a ratio of two band energies, no logarithm.

**Refused outright, with reasons:** signal magnitude area (its 100% result was
**waist**-mounted); spectral entropy (top of no pipeline, needs an FFT *and* a
log); inter-axis correlation (last of 21 features at importance 0.01); jerk
(no study anywhere ranks it or reports a gain); a second magnitude metric
(metric pairs raise r2 by under 0.01).

### One idea worth a cheap experiment

**Self-calibrate the orientation reference from detected skating.** The APE
method computes the angle between the epoch's mean acceleration and an upright
reference, and derives that reference from *automatically detected walking*
qualified by MAD between 150-350 mg. Reported >90% posture accuracy and a
sitting-vs-standing optimum at 11.6 degrees.

Mapped here: instead of asking the player to stand still for ten seconds,
derive the playing-posture reference from confidently detected skating in the
first shift, then score each second by angular distance from it. Fully
hands-free, no UI at all - which is the only kind of calibration this app can
have. **Flagged honestly:** that paper states APE is not validated for the
wrist, its authors put the device on the hip for posture, and the mechanism
above says an arm hanging down looks the same sitting or standing. A cheap
experiment, not a literature-backed gain.
